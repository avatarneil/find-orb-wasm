The compiler finding that matters most

Both targets use binary64 double. On the tested Apple ARM host, long double has 53 significand bits; the pinned wasm32 Emscripten build has 113. Consequently, compiling identical solver source for native and WASM does not guarantee identical intermediate precision. The recorded vector kernels use double; their matching hash does not cover long-double solver calculations.

The probes use -fno-fast-math -ffp-contract=off. Keep these policies across all numerical dependencies. Clang documents that contraction may fuse expressions and fast-math permits otherwise invalid algebraic assumptions; its floating-point manual explains the flags. The actual callback adapter is also exercised on both targets, where Emscripten requires correctly typed function-pointer calls.

Why compact ephemerides can preserve accuracy

DE440 has 32-day coefficient records. Throughout its supported dates, binary64 Julian dates lie on a 2−31-day grid, so one record spans 236 ticks. Date differences fit within 53 significand bits, and division by 32 is exact. Moving the file origin by a whole record therefore changes the integer record number without changing the fractional interpolation coordinate.

The proof models the reader's boundary rule: an exact record boundary uses the preceding record at coordinate one. At the cropped file's very first instant, that record is absent. The strict lower boundary avoids this discrepancy. The integer-grid correspondence to binary64 is a reviewed mathematical assumption; the proof does not validate the compiler's implementation of the operations.

Guard audit: the actual pl_cache.cpp patch loads metadata through sentinel −2 before dereferencing any output pointer, retains sentinel −1 cleanup, rejects missing/out-of-range/NaN JPL queries, and exits after JPL evaluation failures. BC405 asteroid requests return through a separate path and are outside this JPL guard. Upstream's metadata helper truncates JD endpoints to integers; use the distribution manifest for the exact half-day endpoints.

An exact arithmetic optimization

The experimental wideMultiply helper replaces expensive 128-bit intermediate additions with four-by-four base-232 limbs. Each update is value = a[i] × b[j] + out[i+j] + carry. Its maximum is (232−1)² + 2(232−1) = 264−1, so the uint64 accumulator does not overflow.

Thirty-one additional obligations prove the carry decomposition, zero destination for each final row carry, weighted-digit product invariant after every row, and exact 256-bit result for all unsigned 128-bit input pairs. The actual compiled helper also matches JavaScript BigInt on 36,868 input pairs, including every pair of single-bit inputs and 10,000 cases forcing a zero low-64 operand in both orders. The specialized branch computes an exact 128×64 product and shifts by 64; its swap, carry, and output invariants are also proved. The corresponding C-to-model translation is manually reviewed and the header hash is checked before each run.

The optimization changes only the integer product feeding the existing compiler-rt binary128 normalizer and rounder. Their input bits are preserved under this proof's assumptions. It does not reduce long-double precision. The proof results and independent compiler oracle results establish this helper's behavior; actual linked-symbol selection and end-to-end speed and accuracy require separate benchmark evidence.

What remains outside the guarantee

No proof currently bounds cumulative integrator error, nonlinear fit convergence, covariance conditioning, astronomical model error, or observation uncertainty. Neither the C++ frontend, LLVM/Binaryen transformations, binary128 normalization/rounding routines, nor browser engines were formally verified here. Sanitizers and differential tests cover their exercised code and inputs only. NaN payload/sign bits are normalized in the vector hash; all other bits, including signed zero, are retained.

The trusted base includes Z3, Python, the expression extractor, source hash checks, and the manually reviewed search/ephemeris abstractions. The SMT obligations return unsat, meaning no counterexample exists in those models. Proof certificates have not been checked by an independent proof kernel. SMT-LIB files are emitted so another solver can replay the obligations; SMT-LIB's floating-point theory defines the IEEE model used for the two counterexamples.

Practical next verification work

  1. Keep a native/WASM accuracy corpus beside every performance comparison. Add poorly conditioned short arcs, long propagation spans, close encounters, and compact-data boundary cases. Measure residual and orbital-element differences with published tolerances.
  2. Prove the next changed numerical kernel, not the entire legacy solver at once. Derive input bounds and use a high-precision or interval reference before approving reduced precision, approximated functions, or reordered reductions.
  3. Use translation validation selectively. Alive2 can validate LLVM transformations, but has no support for interprocedural transformations and requires a compatible LLVM build. The checked-in IR audit is a flag audit, not an Alive2 proof.
  4. Treat verified compilation as a separate project. CompCert supports C and listed native architectures; it is not a drop-in verified compiler for this C++/WASM pipeline. Frama-C's experimental Frama-Clang frontend is another possible route for isolated annotated kernels.
